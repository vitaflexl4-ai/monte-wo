# MONTE WO — web deployment (Cloudflare Pages + Functions)

**No deployment command was run by this work.** However, the Pages project **`vitaflex-monte-wo` is already connected to this GitHub repository by the owner** (observed on 2026-10-13: every push to `arena/7a19420f-monte-wo` produces a *preview* deployment at `https://arena-7a19420f-monte-wo.vitaflex-monte-wo.pages.dev`, built by Cloudflare from the pushed commit). Consequences the owner must keep in mind:

* **Merging to `main` is a production deployment** of the website + Functions. Open/merge the pull request only when that is intended (the native work is harmless to the site: all new API behaviour is behind `NATIVE_CLIENTS_ENABLED`, default off; migration 0003 is applied only when the owner runs it).
* Preview deployments are public URLs of the branch state; they carry the same honest "not connected" states and no secrets.
* This document records the already-existing deployment path and what must be true before relying on it. All other Cloudflare actions (bindings, variables, Access, DNS) remain owner actions requiring explicit authorization.

## 1. What gets deployed

* Static output: `public/` (generated by `npm run build`; `pages_build_output_dir = "public"` in `wrangler.toml`).
* Functions: `functions/api/[[route]].js` (routes every `/api/*` to `server/`).
* Pages project name in the existing script: **`vitaflex-monte-wo`**, production branch **`main`** (`package.json` → `"deploy": "wrangler pages deploy public --project-name vitaflex-monte-wo --branch main"`). Verify this is the intended account/project before running.
* The app shell is served at `/dashboard/` (`noindex`); the public site at `/`. Making the app the root is a pending product decision — not changed.

## 2. Pre-deployment checklist (owner)

1. **Production origin confirmed** and exported before the build: `SITE_ORIGIN=https://<confirmed-domain>` (HTTPS origin only, no path/port). Without it the build intentionally emits no canonical URLs or sitemap (`docs/website/OPERATIONS.md` §"Production origin and metadata"). The same origin becomes the privacy-policy / support / account-deletion URL for both stores.
2. **Bindings** (only if the corresponding feature is wanted now): `DB` (D1) with migrations applied in order; `WORKOUT_GIFS_BUCKET`; `RANKING_EVIDENCE` (private). Without them the site stays fully functional and the waitlist/Strength Index honestly report "unavailable".
3. **Variables/secrets** as in `.env.example`. Secrets only via Pages encrypted secrets — never in `wrangler.toml`, Git or client code.
4. **Cloudflare Access** application on `/api/strength/*` (self-hosted app; public exceptions for `/api/strength/config` and `/api/strength/catalog`) before `RANKING_ENABLED=true`. Leave `RANKING_PUBLISH_ENABLED` false.
5. **Native clients (optional, later):** `NATIVE_CLIENTS_ENABLED=true`, migration `0007_native_auth_codes.sql`, Access public exception for `/api/strength/native-token`, Access CORS allowing `https://localhost` and `capacitor://localhost` with headers `cf-access-token, content-type` — see `ARCHITECTURE.md` §6. Until then the apps work offline and say so.
6. **Agent API (optional; off until the owner opts in):** enabled only through the production deploy script — `node scripts/deploy-intelligence.mjs --with-agent-api` or `"with_agent_api": true` in `deploy.config.json` for the GitHub workflow. That deploy binds `AGENT_DB` to `monte-wo-intelligence` (same database as `INTEL_DB`; never the waitlist database), applies `0008_agent_api.sql` once (`d1 execute --file`, gated), sets `AGENT_API_ENABLED="true"` and verifies `/api/agent/whoami` → 401. Back up first (`npx wrangler d1 export monte-wo-intelligence --remote --output …`). Keys via `node scripts/agent-key.mjs create … --remote --database monte-wo-intelligence` (least privilege). `/api/agent/*` sits outside the Access application, so no Access change is needed. Bindings added only in the dashboard are dropped by the next scripted deploy — plan, rollback and verification: `docs/release/AGENT_API.md` §1/§8.
7. Review `public/_headers` (security headers / caching) and `public/_redirects` as currently committed.
8. Do **not** touch `flex-ai-db`, other VitaFlex projects, or DNS as part of this deployment.

Already in place (observed): the GitHub repository is connected to the Pages project with build command `npm ci && npm run build` and output directory `public`, Node 22, Python 3 available in the Pages build image; set `SITE_ORIGIN` as a build variable. Either path produces identical output (the build is byte-for-byte reproducible — verified twice in this step).

## 4. Post-deployment verification (manual, owner)

* `GET /`, `/dashboard/`, `/privacy/`, `/terms/`, `/delete-account/`, `/strength/`, `/exercises/`, `/strength-lab/`, `/tools/` → 200 with expected titles.
* `GET /api/status` → readiness JSON; `GET /api/waitlist/config` → `available:false` until configured; `GET /api/strength/config` → readiness without athlete data.
* Service worker updates (hard reload once), 404 page, mobile navigation at 320–1440 px (the browser suites cover these locally).
* Only after this verification may the site, waitlist or rankings be described as live.

## 5. Rollback

Cloudflare Pages keeps every deployment; roll back by promoting the previous deployment in the Pages dashboard (or `wrangler pages deployment list` → redeploy the previous commit). Database migrations are forward-only (append-only tables); restore from the D1 backup/Time Travel described in `BUILD_AND_SETUP.md` §6 if ever needed.

## 6. Relationship to the native apps

The native shells embed the web build; they do **not** load the production site at runtime. A web deployment therefore never changes an installed app, and an app release never changes the website. Shared code lives in this repository and ships through both channels from the same commit (record the commit SHA in each store release note — see `RELEASE_STATUS.md`).
